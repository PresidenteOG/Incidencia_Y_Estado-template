# Architecture

A user logs in and lands on the incident list. From there they add an incident with a title,
description and priority; it starts as **open**. Editing an incident lets you change its
priority and move it between statuses, and moving it to **closed** makes the service stamp a
close time and store how long it was open, in hours and minutes. Statuses live on their own
screen — the app ships with open, in progress and closed, and you can add or remove them, but
not delete one that incidents are still using.

Spring Boot MVC with Thymeleaf views, Spring Data JPA for persistence, H2 as the database. No
REST layer and no JSON — every response is a rendered HTML page.

![incident-tracker architecture: the browser calls the controllers, controllers call the service layer, the services read and write through Spring Data JPA repositories, and the repositories talk to an H2 database](./docs/architecture.png)

## Layers

| Package | Responsibility |
|---|---|
| `controller/` | `IncidenciaController` and `EstadoController`. Map URLs to actions and return Thymeleaf view names. `IncidenciaController` also handles the session login and logout. |
| `service/` | An interface + `Impl` pair per entity. `IncidenciaServiceImpl` holds the only real logic: default a new incident to *open*, keep the original open-date on edits, and compute the resolution time when an incident is closed. |
| `dao/` | `IncidenciaDAO` and `EstadoDAO`, both `JpaRepository<T, Long>`. The CRUD methods are generated by Spring Data, not written. |
| `domain/` | `Incidencia` and `Estado` JPA entities. `Incidencia` has a `@ManyToOne Estado`, so each incident carries exactly one status. Lombok `@Data` generates the getters and setters. |
| `config/` | `AuthInterceptor` + `WebConfig`. The interceptor redirects any request without a session to the login page; `WebConfig` registers it and excludes the login, logout and static paths. |

## Request walkthrough — closing an incident

1. `GET /Incidencia/updateData/{id}` — `IncidenciaController.update` loads the incident and the list of statuses, renders `Incidencia-update`.
2. The form posts back to `POST /Incidencia` with the incident fields and the selected `estado.id`.
3. `IncidenciaServiceImpl.saveIncidencia` sees a non-null id, reloads the original to keep its opening timestamp, and — because the new status is *closed* — sets the close time and writes `temps_resolucio` as `"<h>h <m>m"`.
4. `IncidenciaDAO.save` persists it; the controller redirects to `/Incidencia` and the row shows the resolution time.

## Data

In-memory H2 (`jdbc:h2:mem:incidenciasdb`). Hibernate creates the schema on startup
(`ddl-auto=create-drop`) and `src/main/resources/data.sql` fills it: three statuses and a
dozen incidents, all invented, with dates set relative to the current time so the list never
looks stale. Nothing is written to disk and there are no outbound calls — the app works with
the network off. Changes made through the UI last until the next restart.

## Login

Session-based. `checkLogin` compares the submitted name and password against a hardcoded
`admin` / `admin` — there is no user table. On success the controller puts the name in the
`HttpSession`; `AuthInterceptor` checks for it on every guarded request. This is a demo-grade
gate, enough to show the flow, not production auth.

## Known simplifications

- Delete actions (`/Incidencia/deleteData/{id}`, `/Estado-delete/{id}`) are `GET` links, not `POST` forms. Fine for a demo; a real build would make them `POST` with CSRF protection.
- No server-side validation beyond the HTML `required` attributes.
- Passwords are compared in plain text — acceptable only because the one account is a public demo credential.

## What was reconstructed for this repo

The source was originally committed without a build. To get it running again this repo adds:
the `pom.xml`, the Maven `src/main/java` layout and a package rename to `com.dam.incidencias`,
the `IncidenciasApplication` main class, `application.properties`, `data.sql`, the
`AuthInterceptor` / `WebConfig` pair, and a context-load test. Two controller imports that had
been cut off in the original are restored, and the cosmetic login check was turned into a real
session gate. The service logic and the Thymeleaf templates are the original work, unchanged
apart from the package line.

## Build and run

```
./mvnw test              # 3 tests: context load, seed data, login check
./mvnw spring-boot:run   # http://localhost:8080
./mvnw package           # runnable jar in target/
```

Verified here: `./mvnw test` and `./mvnw package` both pass on JDK 21+, and the running app
handles create / edit / close / delete for incidents and add / delete for statuses.
